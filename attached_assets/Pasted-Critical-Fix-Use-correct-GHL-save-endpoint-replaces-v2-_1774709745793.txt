Critical Fix — Use correct GHL save endpoint (replaces v2.39.0 location-ID URL guessing)

We captured the exact network call GHL makes when saving a page. The extension's entire meta-update approach is wrong — GHL does not use PATCH/PUT on the page ID. The real endpoint is:

POST https://backend.leadconnectorhq.com/funnels/builder/prebuilt-section/sync/changes

Request payload:

{
  "pageData": { <full page data object> },
  "locationId": "5jorVRA6PKGCAeTffHmA",
  "pageId": "NaKUaWZ1OzCQYr3mx7PA",
  "write": false,
  "isPublished": false
}

Response on success: HTTP 201

{ "prebuiltSectionTemplates": [], "traceId": "..." }

What to build:

Add a new injection step (Approach 5 or append to A2) that POSTs the page data directly to this endpoint after the Firebase write succeeds. Use the same auth token already available in the extension. Extract locationId from the active tab URL (/location/([^/]+)/).

const locationId = tabUrl.match(/\/location\/([^/]+)\//)?.[1];

const res = await fetch(
  'https://backend.leadconnectorhq.com/funnels/builder/prebuilt-section/sync/changes',
  {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${ghlToken}`,
      'channel': 'APP',
      'source': 'WEB_USER',
      'version': '2021-07-28'
    },
    body: JSON.stringify({
      pageData: <injected page data>,
      locationId,
      pageId: builderId,
      write: false,
      isPublished: false
    })
  }
);
// Success = 201

Log the result as A5 syncChanges: ok=true http=201 in the debug output.

Note on write: false: Keep this as false initially to match GHL's native behavior. If the page still doesn't appear after reload, try write: true as a follow-up test — it may trigger GHL to write to Firebase itself.

Do not remove the existing Firebase write (A2) or patchToken steps — keep them as fallback. Add this as a new primary attempt that runs first.
